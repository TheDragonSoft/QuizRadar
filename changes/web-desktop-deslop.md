### Settings scroll-spy fix (rAF-suspended background tab)

22. The Settings side rail / mobile pill highlight did not follow the scroll when `requestAnimationFrame` was suspended (Chrome suspends rAF callbacks whenever the document is not visible — background tab, non-foreground pane — and some automation contexts throttle them). The spy coalesced its only scroll-path state update through `window.requestAnimationFrame`, so in those contexts the page scrolled while the rail kept highlighting the section it had before. Found in the real running app by the parent (live probe: scrollTop 0 → 1424 → 1884 → 2452 with the highlight stuck on `settings-nav-account` / `settings-mobile-nav-account`); the click path was unaffected because it sets the state directly.

Fix (`apps/web/src/views/SettingsView.tsx` + `apps/web/src/views/settings/scrollSpy.ts`): the spy now measures the active section straight from the scroll handler instead of coalescing through an animation frame. The measurement is cheap (three `getBoundingClientRect()` calls for three sections) and browsers dispatch scroll events at most once per rendered frame anyway, so no coalescing is needed to keep the cost down — and measuring in the handler cannot be starved by a suspended frame. A new `observeVisibilitySync()` helper re-measures on `visibilitychange` (when the document becomes visible again) and on window `focus`, so a page that scrolled or was restored while hidden never comes back with a stale highlight.

Preserved unchanged: exactly one active item at a time, Account active by default at the top, `aria-current="true"` on the active rail button AND the mobile pill, the existing active accent treatment and the 2px accent indicator, clicking still scrolls to the existing anchor ids and sets the highlight immediately, `prefers-reduced-motion` still switches anchor jumps to `behavior: "auto"`, no new animation, keyboard focus rings untouched.

Regression coverage (`apps/web/src/views/settings/settingsScrollSpy.test.tsx`): the pre-existing 3 cases are kept and unweakened; 3 cases added — (a) `requestAnimationFrame` stubbed to NEVER invoke its callback, with a probe proving the frame really never ran, and the scroll event must still move the active item (both down and back up); (b) the spy re-measures when the page becomes visible again (asserting it does NOT re-measure while still hidden); (c) the spy re-measures when the window regains focus. Case (a) was verified to FAIL against the old rAF-coalesced implementation (the highlight stayed on account while the page scrolled) and to pass against the fix, so it genuinely reproduces the reported bug rather than merely passing.
